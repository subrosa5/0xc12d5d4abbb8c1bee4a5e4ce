# x12 — зашифровать, распределить, восстановить

Экспериментальная версия **0.2.0**. Независимого аудита ещё нет.

В [Releases](https://github.com/subrosa5/0xc12d5d4abbb8c1bee4a5e4ce/releases) доступны архивы автономных приложений: `x12`, `x12-recover`, `x12-desktop`. Они включают Python и криптобиблиотеки. Для desktop нужна графическая сессия. Сборки не подписаны Developer ID и не нотарифицированы.

## Запуск из исходников

```sh
uv sync --locked
uv run x12 desktop
```

Нужен Python 3.11+ с Tcl/Tk. Для CLI Tcl/Tk не требуется. Программа работает локально, без сервера и телеметрии.

## Сейф и отдельные пароли

```sh
uv run x12 create ./document.txt --out ./my-vault --threshold 3 --shares 5 --per-holder
```

Каждая доля получает свой пароль. Файл шифруется по частям, без загрузки целиком в память, до 1 ТиБ. В каталоге появляются `vault.x12`, файлы долей и отметка `COMPLETE`. Распределите доли разным людям, пароли храните независимо. Исходный файл не удаляется.

```sh
uv run x12 recover ./my-vault/vault.x12 \
  --share ./holder-1.x12share --share ./holder-3.x12share --share ./holder-5.x12share \
  --per-holder --out ./restored.txt
```

Автономный `x12-recover` принимает те же аргументы без слова `recover`. Он читает старый и новый форматы, без Python, репозитория и интернета.

## Заменить участников

```sh
uv run x12 rekey ./my-vault/vault.x12 \
  --share ./holder-1.x12share --share ./holder-3.x12share --share ./holder-5.x12share \
  --per-holder --out ./next-generation --threshold 2 --shares 3 --new-per-holder
```

Создаётся новый ключ и новое поколение долей. Старые доли не подходят к новому сейфу. Старые копии с прежними долями остаются читаемыми.

## Проверить версию

```sh
uv run x12 checkpoint ./next-generation/vault.x12 --out ./latest.checkpoint
```

Храните checkpoint отдельно и передавайте его через `--checkpoint` при восстановлении. Он привязывает операцию к точной версии файла. Сам по себе он не определяет, какая версия самая новая, и не защищает от одновременной подмены сейфа и checkpoint старой копией.

## Передать долю с подтверждением

Устройства создают ключи командой `x12 identity`. Участники сверяют полные отпечатки через независимый канал. Получатель создаёт подписанный запрос, владелец доли подтверждает передачу, получатель импортирует зашифрованный ответ под своим новым паролем. Пароль владельца не передаётся.

Используются библиотечные ML-KEM-768, X25519, ML-DSA-65 и Ed25519. Ответ привязан к запросу и адресату, имеет срок действия и учитывается в локальном журнале однократного получения. Протокол экспериментальный. [Все команды и ограничения](device-protocol.md).

## Проверки

```sh
uv run x12 lab --report ./lab-report
uv run x12 replay ./lab-report/report.json --out ./replayed-lab
uv run x12 reduce examples/failure-trace.json --out ./minimal-error
uv run x12 replay-trace ./minimal-error/trace.json
```

Используются только вымышленные данные. Редуктор сокращает последовательность до минимальной ошибки восстановления реального потокового сейфа. Ожидаемое отклонение повреждённого файла не объявляется уязвимостью.

## Что важно понимать

Ключ восстанавливается на устройстве получателя. Получатель может сохранить ключ и открытые данные. Подтверждение передачи доли не обеспечивает новое согласие на каждое чтение. После аварии может остаться временный файл с уже аутентифицированными частями открытых данных; итоговый путь публикуется только после проверки всего контейнера. Гарантированного стирания памяти Python нет.
